## n8n 为什么需要这些资源

n8n 是一个常驻的 Node.js 进程加一个数据库。容器起来之后，5678 端口一直开着，等外部请求打进来触发 webhook，或者等 Schedule 节点到点执行。它不像静态网站那样没人的时候不占资源。

内存花在两处。一是 Node 进程本身和执行工作流时的峰值，二是 n8n 的编辑器是个不轻的浏览器应用，几个人同时开着调试，服务端要跟着维护会话。1GB 机器扛不住，原因就在这里。

数据库有得选。默认走 SQLite，数据文件就在 `/home/node/.n8n` 目录下，个人用完全够。工作流多了、或者要多人同时编辑，可以切到 PostgreSQL。切库不会让这个目录变得不重要，官方 README 专门用警告框写了这件事：即使换了数据库，仍然必须持久化 `/home/node/.n8n`，因为凭据的加密密钥在里面。

磁盘会随时间涨。执行数据默认保留 168 小时，也就是 7 天。跑得勤的工作流一天几百次执行，7 天的记录加上工作流本身，再加上文件节点读写的内容，30GB 是起步。雨云各机型标配 30GB 企业级 NVMe SSD，需要的话可以按 GB 加盘。

CPU 看并发执行数，2 核能应付绝大多数场景。有自托管指南建议优先选独享核，理由是共享核在邻居负载高时性能不可预测，长期跑定时任务容易撞上。

带宽和流量反而不是瓶颈。webhook 请求本身很小，几百字节到几 KB，流量大头是工作流里调 API 返回的 JSON 和文件节点传输的内容。国内机型给 10M 到 35M 上行、不限流量；美国机型给到 100M 到 500M 对等带宽、每月 1TB 流量。跑 n8n 基本用不满。

## 从一条 Docker 命令到能用的编辑器

官方给的最短启动命令是这样：

bash
docker volume create n8n_data

docker run -it --rm \
 --name n8n \
 -p 5678:5678 \
 -v n8n_data:/home/node/.n8n \
 docker.n8n.io/n8nio/n8n


起来之后浏览器打开 `http://localhost:5678` 就能用。这条命令适合本地试，放到服务器上要改两处：`-it --rm` 换成 `-d --restart unless-stopped`，端口映射改成 `-p 127.0.0.1:5678:5678`，让 n8n 只监听本地，外面走反向代理。n8n 不要直接暴露在公网上。

反向代理用 Caddy 最省事，两行就够：


n8n.example.com {
    reverse_proxy localhost:5678
}


Caddy 会自己去签证书。用 nginx 的话记得加 WebSocket 的 `Upgrade` 和 `Connection` 头，编辑器靠这条连接实时刷新，缺了它会一直弹 "Connection lost"。

域名挂在 Cloudflare 后面有个顺序问题：先把代理关掉（灰云），让 Caddy 把证书签下来，TLS 正常之后再打开代理（橙云）。顺序反了，签发会失败。

第一次用域名访问时，n8n 会让你创建管理员账号。建完之后先别急着搭流程，把下面三件事对一遍。

## 三个最容易卡住的地方

### webhook 触发不了

n8n 生成的 webhook 地址来自 `N8N_HOST` 和 `WEBHOOK_URL` 两个环境变量。这两个值配错，或者根本没配，生成的地址就是 `localhost` 或者容器内部主机名，外部请求打不进来。这是 webhook 不工作的第一原因，比防火墙和反代配置出错更常见。

`WEBHOOK_URL` 要写成带协议和结尾斜杠的完整地址，比如 `https://n8n.example.com/`，并且和 Caddyfile 里的域名完全一致。

### 登录进去立刻掉线

用纯 HTTP 加 IP 访问时，`N8N_SECURE_COOKIE` 必须是 `false`。默认值会让浏览器拒绝在非 HTTPS 源上保存那个标记为 secure 的 cookie，表现就是登录成功、页面一跳转又回到登录页，或者直接报 secure cookie 相关的错误。

改成 `false` 再 `docker compose up -d` 就正常了。等上了 HTTPS，记得改回 `true`。

### OAuth 集成根本配不上

这一点很多人买完机器才发现。Google、Microsoft、Slack 这类 OAuth 集成，服务商要求回调地址是一个真实域名上的 HTTPS 地址，裸 IP 提交不上去。API Key 类的凭据没这个问题，Token 填进去就能用。所以你如果只是想连几个用 API Key 的服务，IP + HTTP 也能跑，代价是登录密码、session cookie 和 webhook 载荷全部明文过网。要给客户用，或者要接 OAuth，域名和证书这一步省不掉。

不想买域名也有办法：`203-0-113-10.sslip.io` 这类通配 DNS 主机名会直接解析到对应 IP，用它去申请 Let's Encrypt 证书就行，记得 443 端口也要放通。

## n8n 2.x 的一个变化：文件节点只能写 local-files

Read/Write Files 节点在 n8n 2.x 里被限制了路径。工作流读写的文件必须放在 `local-files/` 目录下，容器内看到的是 `/files`，其他路径一律被拒。

这条在前排教程里基本没人提。如果你从旧版本升上来，之前写在 `/tmp` 或者某个绝对路径下的工作流会直接报错，而且报错信息不会告诉你"是版本限制"。升级前先查一遍所有涉及文件读写的节点，把路径挪到 `local-files/` 映射的位置。

另外，升级前记得翻一遍官方的 Breaking Changes 文档。n8n 迭代很快，镜像标签除了默认的 stable，还有 `next`（不稳定）和具体版本号。生产环境锁定具体版本号，别用 `latest`。带 `-pc` 后缀的标签是 n8n Cloud 内部用的压缩变体，官方明确说没有支持与稳定性保证、可能随时消失，不要拿来部署。

## 备份与恢复：加密密钥是凭据的生死线

`/home/node/.n8n` 目录里放着凭据的加密密钥。工作流丢了可以重建，密钥丢了，所有已存的凭据全部解不开，只能一个一个重新授权。

一份公开的部署脚本是这么做的：PostgreSQL dump、n8n 数据目录、local-files 和 `.env` 副本一起打包，自动保留 30 天，建议用 crontab 每天凌晨 2 点跑一次。它同时提醒了一句关键的话：这些备份躺在同一块磁盘上，要定期拷到服务器外面去。

恢复分三步：停掉 n8n，把 dump 灌回数据库，解包数据目录，再启动。命令大概长这样：

bash
docker compose stop n8n
gunzip -c backups/db_YYYYMMDD_HHMMSS.sql.gz | docker compose exec -T postgres psql -U n8n -d n8n
sudo tar -xzf backups/n8n-data_YYYYMMDD_HHMMSS.tar.gz -C .
docker compose start n8n


`.env` 里的 `N8N_ENCRYPTION_KEY` 必须和备份时的值一致，否则凭据还是解不开。更稳的做法是用 `offen/docker-volume-backup` 这类工具把卷同步到对象存储，Cloudflare R2、Backblaze B2 都支持，成本一个月几块钱。

监控也值得花半小时配一下。Grafana Cloud 的免费额度够个人用，接 Linux server integration 之后，至少设这几个告警：磁盘超过 90%、CPU 持续 5 分钟超过 90%、内存超过 90%、容器 down、5678 端口无响应、备份任务 24 小时没跑。
